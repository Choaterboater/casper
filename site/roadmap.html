Roadmap

Where Casper has been, and where it is going next. Released things first. Then the things still on the workbench.

How to read this page

Released means you can install it today. Every Casper release so far is an early preview: not signed, and not a stable release. A published release is never changed; every fix ships under a new version number.

built, not released means it is built and in the code, and ships with the next preview.

planned, not started means it is the next thing planned, with a version number. Nobody has started building it yet, and the details may still change.

idea, not scheduled means it is agreed as a direction, but has no version and nobody is building it yet.

Released

Newest first. The full notes for each one are in RELEASE.md and on the Releases page.

v0.2.22 · One box for every yes, a network server Casper sets up current preview

Every question that lets something happen is the same numbered box, Casper sets up its own network server, and device checks ask before they touch anything.

  • Casper sets up its network server. Ask about ClearPass, Marvis or an SSID, or about Mist, Central or Wi-Fi next to a network word, or type /mcp setup network: 1 Not now · 2 Set it up. 2 installs casper-network-mcp 0.1.1, every package checked by hash, and connects it with writes off. No file to edit, no variable to set.
  • Your own servers the same way. casper new network-mcp now builds a server with a --read-only start flag, the change kind on every tool that changes things, and an access_check that says where the login can change things.
  • Logins on first use. The first time the AI uses a product, Casper asks you for its login (1 Not now · 2 Add a login), typed hidden, kept in Casper's own private file. The AI never sees it. Casper says where it reaches: Mist login: can change Branch-12 (checked). Central shows saved (not checked) for now, and means new Central (GreenLake) only. A login the product turns down asks 1 Not now · 2 Replace the login.
  • One box for every yes. 1 No · 2 Yes, this once · 3 Yes, for this session · 4 Yes, always for this project, only the answers that fit. One key picks, Esc is No, and nothing asks you to type yes any more.
  • Change kinds. Each MCP change is config, troubleshoot, disruptive, firmware, delete or admin. Firmware, deletes and admin changes are off by default; /mcp allow picks them ahead of time. "Yes, for this session" never covers a reboot, a risky kind or a tool that runs commands. "Yes to everything" covers every change on that product, firmware, deletes and admin too, and shows ALLOW ALL in the footer until ctrl+o.
  • Device checks ask first. They can reach any device, only after your answer; the box names every device and those not marked lab. /lab import fills your lab list from a file.
  • Risky lines in the receipt. After a config change the receipt lists each dangerous line the task added: risky configs/sw1.cfg:6 reload (reboots the switch). A report, never a pass or a fail.
  • Steer while it works. Enter during a task goes to the AI at its next step, or waits for after the task. Look-only commands run during work, and provider retries show as they happen.
  • Plainer words. One numbered sign-in list, model errors with the cause and one next step, /settings by number, and casper update for the newest preview.
  • Windows fixes. Undo, session worktrees and browser sign-in work; the installer keeps your PATH entries as they were. The full test suite does not pass on Windows yet.

v0.2.21 · A clearer screen, pages at phone width

The first published build since v0.2.15. It ships everything from v0.2.16 to v0.2.20 below, plus a screen you can turn up or down and stricter page checks.

  • The window title names the conversation. A short name from your first request, with no model call, and ◐ in front while Casper works. A resumed conversation keeps its name.
  • Pick how much you see. /details quiet, normal or detailed; display: in your own config sets the default. Detailed shows a small diff under each edit. Ctrl+T shows the last step in full. The task's result gets a colored edge: green, yellow or red.
  • Pages checked at phone width too. The page check opens each page at 390px as well as desktop width, and fails a page that scrolls sideways or squashes a text field: ✗ /wide at phone width (390px): the page is 650px wide, so it scrolls sideways. A plain Bun or Node site (an index.html and a script that runs its own server file) gets the check too.
  • Browser fill on more fields. Number, email, date, time and range fields work; no-horizontal-overflow can name one element; a recorded browser check now replays even when the model sends an empty scenario along with it.
  • An honest browser line. When the answer says the browser checks passed but Casper's record says they failed or did not finish, the receipt says so: ✗ Browser checks failed: phone — the answer above says they passed.
  • A request at the empty-folder question runs. Type or paste a request there and it runs in this folder instead of counting as a wrong answer.

v0.2.20 · Fewer layers

Less in your way. Casper and the AI do the next step themselves, and things start on, with an off switch.

  • A shorter new-project menu. casper new asks the kind first (Network, MCP server, Web app or dashboard, Python tool, My own), then which one. My own is an empty folder with git.
  • The AI does it. It changes settings in your project itself instead of telling you to edit a file, builds things on by default, and keeps risk notes to one line.
  • One question for outside writes. A write outside the project asks 1 No · 2 Yes, this once · 3 Yes, for this session, naming the folder, for the shell and the AI's edit and write tools alike.
  • Web lookups. web_search and web_fetch read public pages (DuckDuckGo by default, no key). A lookup holding a secret is refused. web: off turns them off.
  • Quieter, more honest numbers. No repeated "not verified" lines; usage shows out, new and cached tokens; a subscription says so instead of a list price.
  • Notes, not pauses, on spend. A task gets a quiet note at about $1 and $5 and keeps going. A limit you say in the request ("keep it under $2") or spend.pauseAt adds the pause.
  • More projects checked. Swift packages get swift test and swift build, and a Python build check only when the build tool is there.
  • Caching that lasts. The long cache only where it costs nothing extra, one tool list per session, and the cache hit rate in /usage.
  • Smaller things. Browser calls with extra blank fields run; a detailed request builds without "plan first"; a one-line receipt when all is well.

v0.2.19 · Asks before reaching other machines

The AI's shell can reach a switch or a server. Now Casper asks first, hides more secrets, and the receipt says what happened over there.

  • Reach this host? Before ssh, scp, rsync, nc and friends, Casper asks Reach 198.51.100.20 (build-server)? with No first. A script run refuses it and never waits.
  • ~/.ssh stays private in the shell too, with the sandbox off. Lab logins in notes, Proxmox tokens and passwords typed into commands are hidden from the AI and the screen.
  • An honest receipt about other machines. It lists what the AI changed there and what Casper stopped before it got there. When the work lands in a project inside the folder, that project's tests run and Casper offers to switch there.
  • A quieter screen. One line per tool call in a box that folds when the AI moves on. The footer shows each task's tokens and cost.
  • tmux and iTerm2 with nothing to set: busy steps go to a pane beside Casper; /tasks lists what runs in the background.

v0.2.18 · Network skills

Short how-to files for the network products you use, built in.

  • Six built-in skills: Juniper Mist, HPE Aruba Networking Central (new and classic), AOS-CX REST, Junos and ClearPass. A request that names the product gets that skill, picked by a local word match with no model call. Each one tells the AI to ask for data first and to stop and ask you before any change. skills.bundled: false turns them off.
  • More SDKs for local search: /references add pyaoscx, pyclearpass, mistapi and junos-pyez.

v0.2.17 · Undo, receipts and a sandbox

The "oops" release. Take changes back, keep proof of what happened, and fence in the shell.

  • Undo and redo. Next: 1 Show diff · 2 Undo after each task; /undo, /redo and /diff work from a private copy of each task's files, also outside git. Undo never overwrites a file you changed since.
  • Saved receipts. /receipt shows the last receipt after a restart, with secrets hidden.
  • A stricter "verified". In the --json result, only a proven change counts as verified, so --require-verification exits 3 for "Checks passed — not proven".
  • A sandbox for shell commands. On Linux (through bubblewrap, a small sandbox tool) and macOS, the AI's shell, checks, services and dev servers write only the project, temp and package caches and can't read ~/.ssh or cloud logins. The AI's shell and checks reach only listed hosts; any other host asks. Services and dev servers keep the machine's network on Linux and reach only listed hosts on macOS. On Windows, or Linux without bubblewrap, the AI's shell asks before each command that changes something (reads like ls don't). --no-sandbox turns it off.
  • An AI security review. After its tools, /security-review offers to run a model over the changes. It asks first and shows the cost; files the scanners flagged are never opened for it.
  • The plan editor asks "Build this plan?" before it builds.

v0.2.16 · Build new things

Start new projects, see pages load after edits, and run network and security checks. Most of it makes no model call, so it costs zero tokens.

  • New projects with casper new. Pick a kind and a name. Casper builds the project, runs its tests and makes the first commit, with no model. The templates: a Python tool, an MCP server for your network (network-mcp), Mist Python scripts (mist-python), a web app, a NOC dashboard, and Aruba CX (AOS-CX) and Junos Ansible projects. The last line says "Ready", never "verified".
  • Page checks. In a web project, after an edit that reaches a page, Casper starts the dev server, opens the changed pages and reports whether they load.
  • Plan first. A request that asks for many things can get a plan before any building starts. You read it, then pick build or stop.
  • Retry on a bigger model. When repairs run out, Casper asks once whether to retry on your bigger model, and shows a rough cost. Pressing Enter stops.
  • Network checks. Casper finds Ansible playbooks and offers ready-made syntax checks for Aruba CX and Junos. Checks against devices reach one only after you answer a numbered box that names every device; the AI can ask, never answer.
  • Security scans. casper security runs free scanners such as gitleaks and semgrep on your project, with no model call. The report says what the tools found. It never calls your code safe.
  • Enter is the safe choice. At Casper's numbered questions, choice 1 never builds, spends tokens, remembers or reaches a lab.

v0.2.15 · MCP for network servers, with writes off

This one is for network people. MCP servers (tool servers the AI can call) such as hpe-networking-mcp, junos-mcp-server, Mist and NetBox now work with Casper. The AI can read. Changing things is up to you.

  • Every MCP server starts with writes off. Write and delete tools are hidden. /mcp writes <server> is the only way to turn them on, and only you can do it. ctrl+o turns them off again at once.
  • Read-only only when the product says so. A server's access_check tool can confirm a read-only login. Anything else shows access not checked.
  • Risky calls ask you. Words like bounce, reboot, delete and rollback always ask. Only your typed yes runs a call.
  • Device secrets hidden from the AI. Known formats (passwords, RADIUS/TACACS keys, Wi-Fi PSKs, SNMP communities) show up as <secret hidden>. Best effort, not every secret.
  • New command: casper mcp check [repo] checks an MCP server you built: its tests, labels, schemas and example configs.
  • Local vendor specs: /references add downloads Mist OpenAPI, Junos YANG or pycentral so you can search them with no model call.

See it in action on the Network page.

v0.2.14 · See it build, trust the result

The receipt got a verdict line, and the screen got livelier.

✓ Verified — the checks pass, and the tests fail without the change

  • Line 1 is the verdict: Verified, Checks passed — not proven, Failed, Incomplete, Not verified or Stopped.
  • Unfinished is not failed. A check that timed out or could not start says ✗ Not checked and is never sent to a paid repair.
  • Already failing? Before a repair, Casper checks if the test also failed before the change, and asks before paying to fix it.
  • Watch it work: a live footer with the task's stages, one line per check as it finishes, and a bell when a long request is done or needs you.
  • Numbered choices: press the number to pick.
  • Git safety: the AI's shell may not run git stash, git reset --hard, git clean and other commands that can throw away your uncommitted work.

v0.2.13 · Casper runs the checks

The first published build since v0.1.0. The big idea arrived here: don't take the AI's word for it.

  • Casper checks its own work by default. After the AI edits files, Casper runs your project's tests, lint and build, and sends real failures back for repair.
  • Request checklist: before a code change, Casper lists the cases your request asks for. You can edit the list, or press Esc to skip it.
  • Scripting: --json streams events, --require-verification exits 3 when a change was not verified, and command line mistakes exit 64.
  • Sign-in fix: the built program can use stored OpenAI Codex, GitHub Copilot, Anthropic and OpenRouter sign-ins. (The 0.2.12 build could not, so it was never published.)
  • Its own settings: Casper uses CASPER_* settings and no longer falls back to Pi's PI_* ones.

v0.1.0 · The first preview

Where it all started. The first published preview of Casper.

  • Tested by hand on macOS. The test run passed 543 tests with 0 failures.
  • Test installs of the Apple silicon build and the Intel build (run through Rosetta) passed. At the time, nothing had run a Linux build on Linux.
  • Known quirk: the login menu adds a new line each time you move, instead of moving the highlight. Fixed in v0.2.13.

Built, not released

Casper doctor · Casper checks and fixes its own setup built, not released

casper doctor (or /doctor in a session) looks over Casper itself and your setup, fixes what it safely can, and names the rest in one plain line each. No model and no tokens.

  • Casper itself. A newer version, or a casper link on PATH that is broken or points at an older copy.
  • Your setup. Config files that do not load (by file and line), a model sign-in that has run out, MCP and language servers that can't start (with the install page for a missing uvx, npx or docker), missing security tools, a sandbox that can't hold commands (with the install line), disk space, and the network server with its saved logins.
  • Fixes it can make. Run casper update, install the security tools (checked by hash), set up the network server again. Each one asks first: 1 Not now · 2 ….
  • For scripts. Exit 0 nothing to fix, 1 something to fix.

v0.3 · Crews planned, not started

Big jobs get a team, on their own.

  • Split, build, review, fix. For a big job the AI starts builders in their own copies of the project, a reviewer for each part and a fixer, then merges and runs the full tests. No command needed.
  • See it work. The status bar shows the crew (crew 2/3 building · 1 reviewing · $0.40); /crew shows each part. Keep chatting; it reports when the parts land.
  • Your limits apply to the crew. A limit said in the request ("keep it under $2", "no crew for this") holds for the whole crew, and the cost is shown as it goes. crew: off turns crews off.

Later, not scheduled

Ideas, not promises

These are agreed directions with no version number yet. Nothing here is being built right now, and any of it may change shape or be dropped.

Vendor packs · one step to set up a vendor idea, not scheduled

Since v0.2.22 Casper sets up its own server for Mist, Central and ClearPass in one step. For any other vendor it still takes four separate steps: connect its MCP server, pick a read-only preset, add its reference docs, maybe add a skill. A pack does all four at once.

  • One command. casper pack add aruba connects hpe-networking-mcp with its safe-read-only preset, adds the Aruba CX and Central references, and adds a "troubleshoot a site" skill.
  • Writes stay off. A pack never turns writes on. Only you can, by answering a change box or typing /mcp writes <server>.
  • Borrowed format. A pack is a folder in the same shape as Claude Code plugins (MCP servers, skills and commands side by side), not a new plugin API. MCP stays the way tools plug in.
  • First packs: Aruba, then Juniper and Mist.
  • Anyone can publish one. Other vendors, partners and you can make a pack and share it from a git repository (casper pack add <url>). Before it is added, Casper lists what it brings (servers, skills, checks) and asks. Writes stay off.
  • Lab packs. A pack can build a whole lab, not only connect a vendor: for example, Proxmox VMs set up as a Mist fabric, with checks that the fabric came up. Lab sites only.
  • Contributing starts with packs. A pack template and a short guide, so someone can add a skill or check for their own gear without learning Casper's code.
  • Vendor plugin formats. If HPE or another vendor publishes its own plugin format, Casper reads it as a pack, with the same rules.

Ask about your infrastructure · chat that investigates your VMs and services idea, not scheduled

Ask in plain words, on demand: "why is my VoIP server rejecting calls?" Casper looks at the logs, services and settings it can reach, says what it found and what it would change, and changes nothing without your yes.

  • Already there: chat in the terminal, ssh to hosts you allow (it asks first), MCP servers with writes off, and the yes/no change box.
  • To add: ready connections for VM platforms (Proxmox first, then others), read-only by default; a "check this service" skill (logs, ports, certificates, recent changes); and a chat you can reach away from the terminal.

Reading untrusted text safely · tools that only hand back strict JSON idea, not scheduled

Some text should never steer the AI: a WordPress log, an email from a stranger, a web form. A quarantined reader reads it in a sandbox, with no tools, and returns only JSON that matches a schema you set (for example sender, subject, asks for a payment: yes/no). The main AI sees that JSON, never the text, so instructions hidden in the text can't reach it.

  • Already there: the shell sandbox, MCP tool arguments checked against their schemas, and secrets hidden in results.
  • To add: the quarantined reader itself (a separate model call with no tools), strict schema checks on what comes back (anything else is dropped), and a way to offer it as an MCP tool such as "read this untrusted email".

Scheduled jobs with an AI on call · recurring tasks that can investigate their own failures idea, not scheduled

Run a job on a schedule, for example "sync time entries from this database to QuickBooks every night". The job itself is a plain script, so it does the same thing every time. When it fails, or a record is missing a code, an AI looks into it, says why, and fixes what it is allowed to.

  • Already there: Casper runs scripts and checks, reads failures, and repairs them in a bounded loop.
  • To add: the scheduler; a written list of what the AI may do on its own when nobody is there to press yes (everything else waits for you, with a summary); and a log of every run and every change.

Terminal check · Casper tries your command-line program like a person idea, not scheduled

The page check opens a web app and looks at it. This does the same for programs that run in a terminal: CLIs, full-screen terminal apps, network scripts, and Casper itself.

  • Runs it for real. Starts the program in a pretend terminal, types keys at the right moments (Enter, Shift+Tab, Ctrl+C) and waits for text on the screen.
  • On the receipt. Each step passes or fails like any other check, with the screen at the moment it failed.
  • Catches what unit tests miss. A note drawn where nobody can see it, a key that does nothing, a prompt that never comes back.
  • Borrowed. Casper already tests its own screen this way; this hands that to the AI for your projects.

Community lessons · learn from each other's fixes idea, not scheduled

When casper learn turns a fixed problem into a skill or check, you can share it. Other people who add the community pack get it for the areas they pick: network, home lab, Windows Server, iOS, web and more. It comes after packs, and it only works once people use it.

  • Proven, not posted. A lesson comes from a run whose checks passed after the fix, and it carries its own small test. One with no possible check is marked unverified and listed after the rest.
  • Only the lesson leaves. Never the code or session it came from. You see the exact text, secrets hidden, before it is shared.
  • Kept clean. Reviewed by hand at first; later, a lesson's own test decides. Flags and runs that failed with it take a bad one down.
  • Someone else's lesson is not yours. Its checks always run in the sandbox and its skills are guidance only, until you copy one into your own.
  • No server. Lessons live in a GitHub repository and arrive as a pack you choose to add.

Tool rules you write · where and when a tool may run idea, not scheduled

Casper already decides which tool calls run, ask or stay hidden. This lets you add your own rules in a file, such as sites and a maintenance window.

~/.casper/policy.yaml (idea only)
- tools: [port_bounce, reboot_device]
  allow: ask
  sites: [lab-*]          # never on production sites
  hours: "22:00-05:00"    # maintenance window only
  • Stricter only. Like presets and labels today, a rule can only make Casper ask more or hide more. It can never skip an approval or turn writes on.
