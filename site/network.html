Network engineer guide

An AI that can reach your switches is handy. It should also know its place. Here is how Casper keeps the AI on a short leash near network gear, and how to hook up your servers.

Why guard rails?

MCP (Model Context Protocol) is a standard way for an AI tool to talk to other programs, called MCP servers. A network MCP server gives the AI tools like "list the APs at a site" or "run a Junos show command".

That is great for looking things up. But the same server may also have tools that bounce a port, push a config or reboot a switch. An AI can misread a question. It can pick the wrong site. It can be talked into things by text it reads. You don't want any of that to reach a core switch at 2 pm on a Tuesday.

So Casper sits between the AI and your servers. It decides which tools the AI can see, which ones need your yes, and how much of each answer the AI reads. No server and no credentials come with Casper. For Mist, Central and ClearPass it can set up its own server for you, after one question; any other server you trust works too.

The house rules

Every server starts disconnected

Finding a server in a config file is not permission. Only your /mcp connect or --mcp connects it.

Writes start off

The server runs with its read-only settings, and every change asks you first. Only you can allow it, one server at a time.

Changes ask in plain words

Any tool above read shows what it changes, then 1 No · 2 Yes, this once · 3 Yes, for this session, and last Yes to everything on <product> this session. Enter is No; otherwise destructive changes always ask. Firmware, delete and admin changes stay off until you allow them, in the box or with /mcp allow <server>.

The AI can't approve

It has no approval token and no write flag it can set. Its ask tool can't answer the change box.

Read-only only when the product says so

Casper's own guesses can only make things stricter. They never call a login read-only.

Known secrets are hidden

Passwords, RADIUS/TACACS keys, PSKs and SNMP communities become <secret hidden> before the AI reads them (known formats only).

Hook up your servers

Casper sets it up for you (Mist, Central, ClearPass)

Ask about Mist, Central, ClearPass, Aruba or Wi-Fi, or type /mcp setup network. Casper asks once:

casper
Casper can set up its network server (casper-network-mcp 0.1.0, about 60 MB from pypi.org, installed with uv into ~/.casper/tools).
It starts read-only. Logins are asked per product the first time you use it.
  1 Not now
  2 Set it up
Type 1 or 2:
  • 2 installs casper-network-mcp at the version Casper pins, every package checked by hash, and connects it with writes off (--read-only). You edit no file and set no variable. It needs uv.
  • 1 is kept: Casper doesn't offer again. /mcp shows how to set it up later.
  • The first time the AI uses Mist, Central or ClearPass, Casper asks you for that login: 1 Not now · 2 Add a login. You type it hidden; the AI never sees it. Use a narrow login, not an admin one.
  • Casper then checks what the login can do, for example Mist login: can change Branch-12 (checked). Mist and ClearPass logins are checked; a Central login shows saved (not checked) for now. Every change asks you in the change box, which names the product: Change in Mist: ….
  • Logins live only in Casper's own private file (~/.casper/network-logins.json). /mcp login mist replaces one; /mcp login mist forget removes it.
  • A one-shot run never installs and never asks for a login. It says what to type in the terminal instead.

Your own servers

Put your servers in ~/.casper/mcp.json. It uses the common mcpServers format. Casper also finds servers you already set up in VS Code and a few other places; /mcp shows where each one came from.

Two kinds of server work. A stdio server is a program Casper starts on your machine (command plus args). An HTTP server is a URL (HTTPS, or plain HTTP to localhost only).

No secrets in the file

Write ${NAME} instead of a token. Casper fills it from your shell only when the server connects. A missing variable fails the connection, and /mcp names the variable, never a value. Every snippet below is an example: paths and names are yours to change.

Casper spots some network servers by what they run (never by the name you give them) and adds a preset: extra rules on top. A preset can send the server's own read-only switch, hide tools while writes are off, or add a hint. It never loosens anything.

hpe-networking-mcp (Aruba Central, Mist, ClearPass, AOS 8 and more)

~/.casper/mcp.json
{
  "mcpServers": {
    "hpe": {
      "command": "uv",
      "args": ["run", "python", "src/hpe_networking_mcp/mcp_servers/tool_router.py"],
      "cwd": "~/src/hpe-networking-mcp"
    }
  }
}
  • Casper knows it by tool_router.py, hpe-mcp-router, hpe_networking_mcp, any HPE_MCP_* env, or its router tools. Use the path to tool_router.py in your own checkout, and set up its credentials the way its own README says.
  • While writes are off, Casper pins HPE_MCP_ACCESS_PROFILE=safe-read-only, HPE_MCP_READONLY=1, HPE_MCP_PRODUCT_ACCESS=read-only and every HPE_MCP_*_WRITES=0. A pin beats your own value.
  • It hides invoke_tool, invoke_tools_batch and write and delete tools. A read router is judged by the real tool: invoke_read_tool asking for port_bounce still asks you.
  • /mcp shows read-only pins sent, not confirmed until the server itself reports its write switches off through access_check.
  • Bonus: its docs tools (lookup_api, search_docs, ask_docs) are always offered to the AI, so it checks the docs before it guesses an API. /mcp docs can add a docs-only copy with no passwords and no device access, after you pick 2 Add it.

junos-mcp-server

~/.casper/mcp.json
{
  "mcpServers": {
    "junos": {
      "command": "uv",
      "args": ["run", "python", "jmcp.py", "-f", "devices.json", "-t", "stdio"],
      "cwd": "~/src/junos-mcp-server"
    }
  }
}
  • Casper knows it by jmcp.py, junos-mcp-server, or its tool names.
  • There is no read-only setting to pin, so Casper hides load_and_commit_config and render_and_apply_j2_template while writes are off, and lets only plain show commands through (more below).
  • Junos commits can be slow, so a Junos call may go 400 s without an answer unless you set callTimeout.

Mist (hosted MCP)

~/.casper/mcp.json
{
  "mcpServers": {
    "mist": {
      "type": "http",
      "url": "https://example.mist.com/mcp",
      "headers": { "Authorization": "Bearer ${MIST_TOKEN}" }
    }
  }
}
  • The URL above is a placeholder. Use the address from Mist's own docs. Casper spots Mist by a mist.com address.
  • The server runs on Mist's side, so Casper can't pin anything there. It says so: Can't pin read-only for this server (it runs elsewhere). Every change asks you in Casper.
  • It also reminds you: Access not checked. Use a read-only (Observer) org token for this server. That token is the real brake. Casper's hiding is a second one.

NetBox

~/.casper/mcp.json
{
  "mcpServers": {
    "netbox": {
      "command": "uv",
      "args": ["run", "server.py"],
      "cwd": "~/src/netbox-mcp-server",
      "env": {
        "NETBOX_URL": "${NETBOX_URL}",
        "NETBOX_TOKEN": "${NETBOX_TOKEN}"
      }

}
  • Casper knows it by netbox in the command, NETBOX_* env, or netbox in the URL. The env names depend on the NetBox server you use.
  • No read-only setting exists, so Casper hides write and delete tools while writes are off and tells you: Use a read-only NetBox API token for this server.

Connect it

  1. Start casper in any folder and type /mcp. Your server shows as disconnected. This makes no connection and no model call.
  2. Type /mcp connect <name>. Casper asks if it should remember the server.
  3. Remember means next time it connects on its own when a task needs it, always with writes off. Casper stores only a keyed hash of the definition. If the definition changes, it asks again.

Some servers are never remembered: project servers, netmiko_mcp, and servers started through a package runner that can pull new code later (npx, uvx, docker run with :latest and friends) unless you pin a version.

Read-only comes from the product

Here is the honest bit. Casper can't look at your Central or Mist account and know what your login may do. Only the product knows. So Casper asks the product.

A server may offer a read-only tool named access_check. It asks each product what the current login may do. Casper calls it once per connection, only when the server marks it read-only and not destructive, and it takes no arguments.

What the product says/mcp showsWhat happens
Every product says read-onlylogin: read-only (checked)Every tool that is not read or diagnostic is hidden and refused. Writes can't be turned on: This login is read-only (access_check). Writes can't be turned on here.
The login can make changeslogin: can make changes (checked)Nothing unlocks. Writes stay off, changes still ask.
Anything else: an error, a slow answer, no access_check at allaccess not checkedNot read-only. The normal rules apply.

Only the parsed answer is used. The server's own text never reaches the AI.

What about a tool the server marks readOnlyHint: true? It gets the label read and runs without asking. That is the server's word, not a check. Casper's labels, word lists and presets can only make things stricter. They never skip an approval and never claim read-only.

For hpe-networking-mcp, the Casper repo has a proposed patch that adds access_check.

What asks first, and why the AI can't say yes

Every tool gets a label. From least to most strict:

LabelMeansAsks you?
readThe server marks it readOnlyHint: true and nothing tightens itNo
diagnosticThe server marked a tool with no other label as diagnostic (through _meta["casper/safety"])Yes
external-actionThe server gave no labelYes
writeChanges somethingYes
execRuns commandsYes
destructiveCan cut service or delete thingsYes

Scary words always ask

A tool whose name has a destructive or run word anywhere is destructive or exec, even if the server says it is read-only. The words include bounce, reload, restart, reboot, halt, shutdown, disconnect, deauth, rollback, erase, wipe, delete, reset, upgrade, exec, shell, command and similar. So bounce_interface, rebootDevice and clearpass-disconnect-session all ask.

Change words (commit, apply, push, enable, configure…) tighten to write, unless the name starts with a read word: show_commit_history stays a read. A few known read tools, like get_config_rollback_status, keep "rollback" as a noun.

The AI can't approve for you

  • No shortcut exists for the AI. There is no write flag and no approval token the AI can set. "Yes, for this session" and "Yes to everything" are yours to give, per server, and end with the session or ctrl+o; under "Yes, for this session" destructive changes still ask.
  • Sneaky arguments ask too. If the AI sets confirm, confirmed, confirmation or force to true (in any spelling, or as "yes" or 1), Casper asks even for a read tool. Same if it turns a preview switch like dry_run off. The box then warns: ⚠ The AI set confirm=true. That skips the server's own check. Only your answer here lets it run.
  • Server questions reach only you. When a server asks "Confirm PORT BOUNCE on SG1 ports [1/1/1]?", the AI never sees the question and has no tool to answer it.
  • No terminal, no approval. One-shot runs can't ask, so a call that needs approval fails with Not executed (needs your approval, and this run cannot ask).
  • A failed call is never retried on its own. A lost answer does not prove nothing happened.

If the tool has a preview switch, Preview first is added after the yes answers: it runs a dry run and shows the box again with the result. Passwords and PSKs in the box show as ••• 13 chars on your screen; the server still gets the real value you approve.

Writes are off until you say so

Every server starts with writes off, remembered ones too. That means the server runs with its read-only settings, and every change asks you first in the change box.

You allow changes from that box: 2 for this one change (writes go back off after it), or 3 for the rest of the session on that server (destructive changes still ask every time). To turn writes on ahead of time, type /mcp writes <server> and pick 2.

  • While any server has writes on, the footer starts with WRITES: <servers> · ctrl+o. It is never cut off.
  • ctrl+o (or /mcp writes off) turns writes off for every server at once, even while Casper is working, ends every "for this session" answer, and denies any open change box. Think of it as the big red button.
  • The AI's ask tool can't answer the change box or the writes box. In a one-shot run, /mcp writes says Writes can only be turned on in an interactive session.
  • If your own settings still keep writes off (say HPE_MCP_ACCESS_PROFILE=safe-read-only in your config), Casper tells you instead of pretending.

Junos: show commands only

junos-mcp-server has no read-only switch, so Casper reads the command text. With writes off, only plain show commands run. Anything else gets Not executed (Junos writes are off; only show commands run.)

A "plain show command":

  • starts with the full word show (no short forms like sh);
  • has no ;, line break or redirection;
  • uses only the pipes match, except, count, display, no-more, last, find and trim (| save is refused).

Show commands still ask, with 3 Yes, show commands on junos for this session in the box (or type /mcp junos-show junos on); after that, plain show commands on that server run without a box, and everything else still asks. PFE commands always ask. And load_and_commit_config gets a plain warning in its box: load_and_commit_config commits right away. No preview and no auto-rollback.

Learning Junos?

/references add junos-yang can download one release of the Junos YANG models (after you pick 2 Download). Then you and the AI can search them on your own disk, with no model call and no restart. pycentral, pyaoscx, pyclearpass and mistapi work the same way.

Secrets in configs are hidden

Device configs are full of secrets. Casper swaps each one it knows for <secret hidden> before the AI reads the text, and keeps the words around it so the AI still knows what kind of line it is. It is on by default.

It covers every MCP result (always), config files you or the AI read (.cfg, .conf, .set, and files under configs, backups or oxidized folders), and command output that looks like a config.

  • The AI can't send a hidden secret back. An MCP call, file edit or shell command that still has <secret hidden> in it is refused, so the marker can't overwrite your real RADIUS key.
  • netconan is an extra check. If netconan is installed, Casper runs it too, after its own rules. It misses some Aruba formats, which is why Casper's rules run first.
  • Only you can turn it down. /secrets files off stops file and command scrubbing for the session. MCP results are always scrubbed. The AI has no way to turn scrubbing off.
Known formats only

This is best effort. Odd formats (EdgeConnect, ClearPass XML exports, JSON with strange key names) can still get through. hpe-networking-mcp's own hpe_mcp_secret_… tokens are left alone on purpose, because that server swaps them back itself. Look at what a tool returns before you share it.

Check a server you built

Writing your own MCP server for your lab? casper mcp check [repo] looks it over before you connect it. It runs the repo's doctor and tests, starts the server once, and lists its tools. It never calls a tool unless you add --live. Even then it calls only access_check and up to 3 tools the server labels read-only; write tools are never called.

It checks that every tool has readOnlyHint or destructiveHint, and that the label fits the name. It checks schemas, confirm and dry_run fields, and your example configs (a plain-text secret or a setting that turns writes on is a problem). It runs your repo's code, so only use it on repos you trust.

From inside your server's repo
casper mcp check . --quick

Add --json for a report a script can read, and --strict to fail on warnings too. Exit codes: 0 no problems, 1 problems, 64 usage mistake.

Walk-through: APs per site in Mist, read-only

A typical first job. You want a list of APs per site, and you want zero chance of a change. Here is the path. (The steps and Casper's messages are real; what the AI says will vary.)

  1. Make a read-only token on the Mist side. An Observer org token. This is the part that really keeps it read-only, because Mist enforces it, not Casper.
  2. Put it in your shell, not in a file. export MIST_TOKEN=…, then add the Mist entry with Bearer ${MIST_TOKEN} to ~/.casper/mcp.json.
  3. Start Casper and look. Type /mcp. You'll see mist as disconnected, with writes off.
  4. Connect. Type /mcp connect mist. Casper reminds you that it can't pin read-only on a hosted server and that access is not checked. Pick 1 for just this session or 2 to remember it.
  5. Ask plainly. "List the APs at each site in Mist. Read only, no changes." The AI finds tools with find_capability (a word like site finds mist_list_sites) and calls them. Tools the server marks read-only run without asking. Anything else stops at the approval box for you.
  6. Big orgs are cut to size. Each result the AI reads fits 16 KiB, and each list is cut to 50 items, with a note like Partial result: … shows 50 of 2000. More: call again with next_cursor. So the AI knows it saw only part, and can ask for the next page.
  7. Secrets stay hidden. If a result carries a PSK or RADIUS key under a key like psk or radius_key, it arrives as <secret hidden>.
  8. Done? Nothing to undo. Writes were never on. If you ever do turn them on, ctrl+o turns them off again for every server.
Why both a token and Casper?

Casper's rules read tool names and labels. They can't see inside a server. A tool that changes things under a read name, marked read-only by its server, would run without asking. A read-only token on the product side covers that gap. Two brakes are better than one.

What Casper can't do

These are practical checks, not a sandbox and not proof of what a server does. Straight from the docs:

  • A server can lie in its labels, or change something from a tool that looks like a read.
  • The name checks are word lists. They read tool names, not what a tool does. The Junos show check reads the command text the same way.
  • Stdio servers run with your user's permissions.
  • MCP servers run outside Casper's shell sandbox, with your user's permissions. On Windows, or with the sandbox off, the AI's shell could read MCP configuration or go around this interface.
  • Secret hiding covers known formats only.

So: only connect servers you trust, and give them logins with only the rights they need. Tool descriptions and results are outside content, not instructions.
