Feature tour

Grab a coffee. This is every big thing Casper did in 0.2.15, one at a time, with the real text it prints. What came after (new projects, undo, the sandbox, network skills, page checks at phone width, Casper's own network server, the numbered approval box) is on the roadmap.

About the terminal boxes on this page

Each dark box is text copied from a real Casper 0.2.15 run. No screenshots, no mock-ups. To keep them free and repeatable, the "AI" in most of them is a small scripted stand-in: it makes one real edit on disk, then says No more changes. Everything after that (checks, proof, repairs, receipts, MCP, approvals) is Casper's own code doing its job. Times like 0.0s will differ on your machine.

Receipts and the verdict line

Every coding task ends with a short receipt. Line 1 is the verdict. The lines under it are the evidence: which files changed, which checks ran, and how long they took.

What you see

A green ✓ Verified only when the checks pass and a test fails without the change. Anything less says so, in words:

• Not verified — the tests pass without the change too

✗ Failed — test failed

✗ Not checked — test timed out, so the change was not tested

Why it matters

"Done" from the AI is a claim. The receipt is what really happened. You can skim line 1 and move on, or type /receipt for the full detail behind it (how each command ran, what it covered, and whether a pass was reused). /receipt makes no model call.

Proof: tests fail without the change

A passing test suite is nice. But if the tests also pass without the change, they did not test the change at all. So Casper checks.

  1. Before the AI starts, Casper keeps a copy of your project.
  2. After the checks pass, it builds the project without the change (old code, current tests) and runs the test check there.
  3. If that fails, and the same check passes with the change, the change is proven.
  4. If it passes without the change too, the change is not proven. Casper spends one repair round asking the AI to add a test that fails without the change, then checks again.

What you see

✓ Proven: test fails without this change (exit 1) and passes with it in the good case. Here, a plain ⚠ Not proven line and the one repair round it tried.

Why it matters

It catches the classic "all green, nothing tested" run. Test-only, docs-only and refactor changes need no proof, and the receipt says why. The comparison runs the test check once or twice more, so it adds that time.

Auto checks and the repair loop

After the AI edits files, Casper runs your project's own checks (test, lint, type check, build) by itself. You don't have to ask. Real failures go back to the AI for a few repair tries: 3 by default, set with repair.maxAttempts (0 to 10).

What you see

The failing check's real output in a box (the last 40 lines; the full log is kept), a ↻ repair 1/1 line, the check running again, and a receipt that tells you what to type next: /verify repair test.

Why it matters

The AI gets the real error text, not a guess. Before the first repair, Casper also runs a failing check on the old code. If it was already broken, Casper says so, and in a terminal it asks 1 Fix it anyway · 2 Leave it before spending tokens.

No paid repair for timeouts

A check that timed out or could not start did not fail as a test. A repair costs tokens and cannot fix a slow suite or a missing tool, so Casper never sends these to a repair on its own. In an interactive terminal it asks you instead:

  1. Retry: run it again with the same limit.
  2. Fix it anyway: ask the AI to fix it (uses tokens).
  3. Allow more time (timeouts only): four times the limit it just had, at least a minute and at most an hour.

Esc skips. You can see the "could not start" version of this question in Numbered choices below. In a chat, checks that take a minute or more are offered as /verify instead of running after every edit. --no-verify turns checking off.

The live view

While Casper works, the screen tells you what it is doing right now, without a wall of text.

Check lines

Each check prints one line when it ends: ✓ lint · 0.1s, ✗ test · exit 1 · 2.3s or ✗ test · timed out after 10m. A pass is never silent.

Tool lines with +N -M

Each tool call is one line in the Working box, • while it runs and ✓ or ✗ once done; the finished steps fold into one summary line, with the changed files named under it. With a real model, an edit line also shows lines added and removed, like +9 -1. (The stand-in above does not send those counts.)

The step rail

The footer lists the stages of the task, each ticked when done, then the time: ⠋ checklist ✓ · building ✓ · checks · 1m05s. In a narrow window it shows only the current stage.

A bell when it's your turn

When a task that ran 10 seconds or more ends, or Casper needs an answer, it rings the terminal bell. Your terminal decides if that is a sound, a flash or a bounce. Scripts never ring.

Why it matters: you can look away, come back, and know at a glance where things are. "Tool finished" never pretends to mean "check passed".

Commands that use no tokens

Plenty of Casper runs on your machine alone. These make no model call, so they cost you no tokens:

  • the checks Casper runs by itself after an edit, and /verify to run them by hand
  • /mcp to see and manage your MCP servers
  • /diff to see your Git changes
  • /receipt for the full detail behind the last receipt
  • /references search over your local reference folders

A repair is different: /verify repair test asks the AI to fix a check, and that does use tokens.

MCP servers and asks

MCP servers are tool servers the AI can call: think Aruba Central, Junos, Mist or NetBox. In Casper every server starts with writes off: every change asks you first, in plain words, and only your answer lets it run.

What you see

What changes, in plain words, one value per line with secrets hidden, then 1 No · 2 Yes, this once · 3 Yes, for this session. Enter is No. A key typed before the box appeared never answers it. A login shows as read-only only when the product itself says so; otherwise it reads access not checked.

Why it matters

A bad guess on a core switch is not a failed unit test. The AI cannot approve anything for you, and text typed early cannot answer a later ask. More on this, with presets for known network servers, on the Network page.

Check an MCP server you built

casper mcp check looks at your own server: its tests, whether its tool labels match what the tools do, and whether its example configs keep writes off. It runs the repo's code, so use it on repos you trust.

Secrets hidden from the AI

Device configs are full of passwords, RADIUS keys and SNMP communities. Casper swaps the ones it knows for <secret hidden> before the AI reads the text, and tells the AI how many it hid.

What gets scrubbed

  • MCP results: always.
  • Files read: config files only (.cfg, .conf, .set, or files under configs, backups or oxidized).
  • Command and grep output: when it looks like a config.
  • Reference search excerpts.

The honest part

This is best effort. It hides known formats, not every secret. Odd formats (EdgeConnect, ClearPass XML, JSON with strange key names) can slip through. Look at what a tool returns before you share it.

References search

Point Casper at folders on your disk (an SDK, a vendor API spec, Junos YANG models, your own scripts) and search them with no model call. The AI gets a read-only search_references tool for the same folders, so it can look at real examples instead of guessing.

/references                          list your sources
/references search pycentral vlan    search one source
/references search * schema routing  search all of them
/references add pycentral            download a known spec repo (asks first)

What you get

Up to 8 matching lines, each with its file, line number and the file's SHA-256. Every word you type must be on the same line. It is plain text search: no regex, no "meaning" search, no ranking. The output is JSON.

Handy for network folks

/references add knows the Junos YANG models (junos-yang, pick a release, such as 23.4) and the Central, AOS-CX, ClearPass, Mist and PyEZ SDKs. It shows the exact git commands and runs them only after you pick 2 Download.

Scripting: --json and exit codes

Give Casper a prompt on the command line and it does that one task, then exits. Add --json and every event is one JSON object per line on stdout. The last line is the receipt.

Exit codes a script can trust
CodeMeaning
0Done. Changes were verified or, without --require-verification, not disproven.
1Failed: a check failed, checks were blocked, or the model run failed.
2Incomplete: a check could not finish, --max-turns stopped it, or checking was asked for and no check exists.
3Not verified. Only with --require-verification.
64Usage mistake, such as a typo in a flag. Nothing ran, and no paid prompt was sent.
130 / 143Cancelled (Ctrl-C) / terminated.

Why it matters: a CI job can fail on "not proven", not just on "tests red". Handy flags: --model, --continue, --verify, --require-verification, --max-turns. A lone - reads the prompt from stdin, which keeps it out of ps.

Sessions

Conversations are saved per folder, so you can pick up where you left off, or try a risky idea on the side.

casper --continue        carry on with this folder's last chat
/resume                  list saved chats; /resume <id> brings one back
/clear                   start fresh (the old chat stays resumable)
/branch try-evpn         a named branch, in its own Git worktree
/tree                    show main and every branch
/switch main apply       check, review and apply the experiment to main
/switch main discard     review, then drop it

What you see

Branching and switching ask for a typed yes. apply runs your checks in the experiment folder first, shows the full diff and its SHA-256, and applies that exact patch to main without committing.

Worth knowing

Bringing back a chat does not undo file changes. "Discard" means "do not apply": the experiment's files are moved to a recovery folder under ~/.casper/worktrees/, and Casper never deletes those. Clean them up yourself.

Numbered choices

When Casper needs a decision, it shows numbered answers. Press the number. Or use Up/Down and Enter, type your own answer, or press Esc to skip.

Why it matters: one key, no typing out long answers, and nothing expensive happens behind your back. The MCP change box above works the same way: it says what changes, and only your 2 or 3 lets it run.

Rich or plain terminal

On a rich terminal at least 58 columns wide, Casper opens with its ghost and wordmark. Boo.

Rich

Colors, a live footer, lines that update in place, and boxes for code, diffs and failed check output. Color always comes with a readable symbol or word, so nothing is color-only.

Plain

NO_COLOR keeps the layout and drops the color. TERM=dumb or redirected output gives plain text lines, and a narrow window gets a one-line CASPER 0.2.22 · your coding companion header instead of the art.

What does /help show? 
❯ /help
Casper — your coding companion

Type a request and press Enter (during a task it steers the AI or waits in the queue). Esc stops work. Type / for every command.
  casper [folder]        Open Casper here, or in that folder
  casper <prompt>        Run one request and exit (options: /help all)
  casper new [name]      Start a new project (casper new --list shows the kinds)
  /model, /effort        Pick the model, and how hard it thinks (Shift+Tab cycles effort)
  /diff, /undo, /redo    See the last task's changes, or put its files back
  /verify, /receipt      Run this project's checks (/verify add saves one Casper found); what the last task did
  /mcp, /lab             Tool servers (writes off until you turn them on); your lab devices
  /mcp setup network     Set up Casper's server for Mist, Central and ClearPass; /mcp login adds a login
  /references            Search vendor specs you downloaded (/references add gets one)
  /resume, /clear        Pick up a saved conversation, or start a fresh one
  /settings              Turn web lookups, spend notes and other switches on or off by number
  /help <word>           Search the help; /help all shows everything
Ctrl+T shows the last step in full. Ctrl+C twice on an empty line exits. Approvals always need a fresh yes from you.
