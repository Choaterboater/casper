# Hard pack: does Casper's receipt catch wrong outcomes? 2026-09-26

**Result: the decision rule is not met.** Casper's receipt said `verified` on all 12 wrong Casper runs (caught
0/12, Wilson 95% 0-24%, against the 70% bar). By the agreed rule, Casper shrinks to a Pi extension instead of
continuing as a harness. Nothing in this run argues against the verdict: the interval's upper bound is far
below the bar, and every one of the 12 misses is a stated requirement.

Models: GLM 5.3 Flash (`--route Together`) and DeepSeek V4.1 Flash (`--route DeepSeek,Together`), `--time-limit
600`, concurrency 3 per model. Pack frozen at `791aa05` (branch `phase/hard-pack`). Raw results:
`.scratch/hard/decision/` (`*-paired.json`: casper, casper-review and pi side by side at repeat 2; `*-casper.json`:

## Why the receipt missed every one

Every wrong Casper run passed the visible tests, and Casper's proof (the test fails without the change and
passes with it) held. So `verified` meant what docs/VERIFICATION.md says it means: the commands passed and the
change is proven against them. It does not mean the requested behavior is complete. The misses were
requirements that neither the visible tests nor the model's own tests checked:

| Misses | Task | Hidden requirement |
|---:|---|---|
| 5 | `hard-rate-limiter` | `retryAfterMs` exact to the millisecond after a fractional refill (float drift gives 2 ms instead of 1) |
| 1 | `hard-rate-limiter` | never more than `capacity` after a long wait |
| 2 | `hard-conditional-http` | `PUT` with `If-None-Match: *` creates (201 + Location) and is 412 on an existing document |
| 1 | `hard-conditional-http` | behavior right, but `CONTEXT.md` edited against the prompt's rule |
| 2 | `hard-money-allocation` | malformed amounts / unknown currencies rejected |
| 1 | `hard-job-queue` | priority order |

Even without the five float cases, 0 of 7 were caught. The review round (`casper-review`) did no better on its
two misses, and its token cost broke the 1.25× bar.

## How the pack got here

- Six new tasks (`evals/packs.ts` `HARD_PACK`, docs/EVALUATION.md "The hard pack and receipt honesty"): stub
  starts that fail the visible tests, visible tests on the basic path only, every hidden check stated in the
  prompt.
- **Calibration missed its band.** The agreed target was 25-60% failures on Pi. Round 1 had 3 fair misses in 24
  runs (two further GLM config misses were the grader's fault: the prompt did not say what an env variable
  below a non-object key is, now stated). Round 2 added 2-3 stated requirements per task and fell to 2 of 24:
  both models implement an explicit spec reliably. The owner chose to freeze the pack and get the wrong runs
  from volume, at half the recommended volume (8 Casper runs per task per model instead of ~17).
- Round 2's Casper timing pass did not start (its runner exited after the Pi runs, with no log). The time check
  rests on round 1 (Casper max 184 s) and round 2's Pi medians (max 158 s); the decision run had one timeout in
  96 Casper runs (1%, under the 10% bar).
- During the decision run another Casper session changed the default `verification.timeoutMs` from 600 s to
  1800 s in the working tree (`src/config/load.ts`), and ran the full test suite twice. The hard-pack checks
  finish in under a second and every run is capped at 600 s, so the change had no effect on these runs; the extra
  CPU load fell on all three harnesses, which run side by side.

## What this means

The receipt is honest about what it checks (commands and proof) and silent about what nobody tested.
The catch rate on the failure that matters, a plausible change that passes its own tests, is 0 of 12.
Under the owner's rule, Casper's checks, proof and receipt continue as a Pi extension. Anything that would catch
this class needs evidence beyond the model's own tests: that is the open question for the extension, not a reason
to keep the harness.

**Superseded the same day:** the owner reversed the Pi-extension call. Casper stays its own product, with Pi's
SDK as a pinned library, and the extension was not built. The follow-up experiment is
[2026-09-26-acceptance-check.md](2026-09-26-acceptance-check.md).
