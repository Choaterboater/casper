# Phase 6 (Run & observe): pinned acceptance, 2026-09-26

Models: GLM 5.3 Flash (`--route Together`) and DeepSeek V4.1 Flash (`--route DeepSeek,Together`),
`--time-limit 600`, Casper at its default (review off). Raw results: `.scratch/phase-6/accept/`
(`a-*` acceptance, `r-*` Casper rerun, `c-*` regression) and `.scratch/phase-6/baseline/`.

## Before Phase 6

The post-4a baseline had `core-rest-validation` and `core-ui-tabs` at 24/24 for Casper and Pi, so the
original acceptance ("Complete/success improves") could not move. It was replaced by: (a) Casper starts
the service, calls the new endpoint and shows a passing smoke check with a failing baseline; (b) a new
task, `core-service-lifecycle`, where only running the server shows the behavior; (c) no regression.

## Results

| Task | Casper right | Pi right | Casper / Pi median wall |
|---|---:|---:|---:|
| `core-rest-validation` (6 + 6 Casper runs, 6 Pi) | 12/12 | 6/6 | 53 s / 54 s (no services line) |
| `core-service-lifecycle` (Casper rerun, 3 per model) | 5/6 (1 false done, GLM) | 6/6 | 194 s / 153 s |
| `core-ui-tabs` + 5 pinned tasks (Casper, 2 per task per model) | 23/24 (1 false done, GLM `core-mcp-tool`) | – | at baseline within noise |

- **(a) met only with a first-turn line** naming the services and asking for a check before editing:
  every run then used the `service` tool (7-22 calls) and model checks with a failing baseline passed
  (GLM 2/3, DeepSeek 3/3). Without the line no model called the tool in 12 runs. The line tripled
  `core-rest-validation` (149 s, 22.5 turns, 390k tokens against 53 s, 10.5 turns, 103k) with no
  correctness gain, so it was **dropped**; configured smoke checks still run and pass on every run.
- **(b) not met on GLM** (5/6 overall against Pi 6/6). In the false done Casper's receipt said
  `not_verified`: the model's words claimed done, Casper's outcome did not.
- **(c) time met without the line; the ±10% token rule cannot be judged at 2 runs** (the same
  prompt varied −44% to +100%). The pinned tasks declare no services, so their loadout is unchanged by
  construction (tested over the exact pack prompts).
- **Found and fixed:** a model's `pkill -f` with words from the prompt killed every Casper run on the
  task (3 runs, exit 143): Bun cannot retitle a process as Node (Pi) does, so the prompt argument
  stayed in the process list. Casper now reads a lone `-` prompt from stdin, and the harness uses it.

## Receipt honesty across all pinned runs so far

99 Casper runs with a receipt: 84 verified and right, **3 verified but wrong** (all the same
`core-mcp-tool` requirement, "files in path order", that the model's tests never asserted), 3 wrong
and caught (not verified), 9 right but not verified. Pi: 60 runs, 3 wrong, all 3 reported done.
The tasks are too easy (6 wrong runs in 99) to establish the catch rate: that is the next experiment.
